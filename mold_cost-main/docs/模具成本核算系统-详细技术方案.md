# 模具成本核算系统 - 详细技术方案

## 一、项目概述

### 1.1 项目目标
构建一个基于AI Agent的模具成本核算系统，实现从CAD文件上传到成本报表生成的全自动化流程。系统采用微服务架构，通过MCP（Model Context Protocol）协议实现Agent与专业服务的解耦，支持线割、NC加工等多种工艺的成本计算。

### 1.2 核心技术栈
- **后端框架**: FastAPI（Python 3.11+）
- **AI框架**: LangChain + LangGraph（状态机编排）
- **大模型**: GPT-4或Claude（Agent决策）
- **消息队列**: RabbitMQ（异步任务处理）
- **数据库**: PostgreSQL（业务数据）+ Redis（缓存与状态）
- **对象存储**: MinIO（文件存储）
- **实时通信**: WebSocket（进度推送）
- **容器化**: Docker + Docker Compose
- **协议标准**: MCP（Model Context Protocol）

### 1.3 项目周期与人员分工
- **项目周期**: 6周（第一期核心功能）
- **团队规模**: 7人（ZQY和ZZH负责Agent编排与API网关）
- **开发模式**: 敏捷开发，每周迭代

## 二、系统架构设计

### 2.1 整体架构
系统采用分层架构设计，从下至上分为：
1. **基础设施层**: Docker容器、数据库、消息队列、对象存储
2. **MCP服务层**: CAD解析、特征识别、NC连接器、价格服务、报表生成
3. **Agent层**: 编排Agent、CAD Agent、特征识别Agent、决策Agent、计价Agent、报表Agent
4. **API网关层**: 统一接口、认证鉴权、请求路由
5. **前端展示层**: React单页应用、WebSocket实时通信

### 2.2 核心组件说明

#### 2.2.1 API网关
使用FastAPI构建RESTful API网关，负责：
- JWT Token认证与用户身份验证
- 文件上传接收与格式验证（DWG/PRT，最大100MB）
- 病毒扫描集成（ClamAV）
- 请求日志记录与追踪（生成request_id）
- 跨域资源共享（CORS）配置
- 限流与熔断保护

#### 2.2.2 消息队列系统
RabbitMQ作为异步任务调度中心：
- **job_processing队列**: 接收新任务，触发编排Agent
- **recalculation_queue队列**: 处理重算请求
- **死信队列**: 处理失败任务，支持重试
- **消息持久化**: 确保任务不丢失
- **并发控制**: 4个Worker进程，每个Worker并发2个任务


#### 2.2.3 数据存储系统
**PostgreSQL数据库**（17张核心表）：
- **users表**: 用户信息，支持RBAC权限管理
- **jobs表**: 任务主表，记录任务状态、进度、总成本
- **subgraphs表**: 子图详细信息，包含业务数据和成本
- **features表**: CAD提取的特征数据，支持版本历史
- **job_price_snapshots表**: 每个任务的价格快照（用户可修改）
- **job_process_snapshots表**: 每个任务的工艺快照（用户可修改）
- **price_items表**: 价格库主表，支持版本管理
- **process_rules表**: 工艺规则库主表，支持版本管理
- **user_interactions表**: 用户交互记录
- **operation_logs表**: Agent操作日志
- **audit_logs表**: 审计日志，记录所有数据变更
- **reports表**: 报表文件记录
- **report_summary表**: 报表汇总数据
- **archives表**: 归档记录
- **recalculations表**: 重算记录
- **batch_recalculations表**: 批量重算记录
- **nc_calculations表**: NC计算记录（审计和Phase 2使用）
- **login_logs表**: 登录日志

**Redis缓存**：
- 任务执行上下文（job:job_id:context，TTL 24小时）
- 分布式锁（job:job_id:lock）
- 会话状态缓存
- 热点数据缓存（价格库、规则库）

**MinIO对象存储**：
- **files bucket**: 原始DWG/PRT文件（保留30天）
- **reports bucket**: 生成的Excel/PDF报表
- **archives bucket**: 归档数据（保留7年）
- **temp bucket**: 临时文件（保留7天）

#### 2.2.4 MCP服务层
基于Model Context Protocol标准，每个MCP服务独立部署：

**CAD解析服务（cad-parser-mcp，端口8101）**：
- 使用Open CASCADE或类似CAD内核
- 提供parse_dwg、parse_prt工具
- 实现split_subgraphs拆图算法（图层识别、封闭轮廓检测、DBSCAN聚类）
- 支持2D转3D拉伸（extrude_2d工具）
- 支持3D PRT拆分（split_3d_by_region工具）

**特征识别服务（feature-recognition-mcp，端口8102）**：
- 基于几何算法识别封闭轮廓
- 计算线割长度（周长计算）
- 提取厚度信息（从尺寸标注或文本注释）
- 判断是否需要线割（封闭性检查）
- 返回置信度评分

**NC连接器服务（nc-connector-mcp，端口8103）**：
- HTTP客户端，调用外部统一NC Agent
- 外部NC Agent提供完整的NC计算能力（钻孔、开粗、精铣）
- 实现超时重试机制（3次，指数退避）
- 降级策略（使用默认值或历史平均值）
- 异步调用（asyncio）

**价格服务（pricing-server-mcp，端口8105）**：
- 价格匹配算法（数据库查询+条件过滤）
- 成本计算引擎（面积计算、时间计价）
- 特殊规则应用（慢丝加成、批量折扣、材料加成）
- 支持多种计价单位（元/mm²、元/小时）

**报表生成服务（report-generator-mcp，端口8107）**：
- 使用openpyxl生成Excel报表
- 使用ReportLab生成PDF报表
- 多Sheet结构（成本汇总、子图详情、计算依据、操作记录）
- 支持公司Logo和水印
- 生成预签名下载URL（有效期24小时）


#### 2.2.5 Agent层设计
所有Agent继承BaseAgent基类，实现统一接口：

**OrchestratorAgent（编排Agent）**：
- 使用LangGraph构建状态机，定义8个阶段的流程
- 加载配置文件（workflow_config.yaml、routing_rules.yaml、agent_registry.yaml）
- 动态调用其他Agent，传递执行上下文
- 管理任务状态转换（pending → processing → completed/failed）
- 处理异常与回滚
- 记录详细操作日志

**CADAgent（CAD解析Agent）**：
- 调用cad-parser-mcp服务
- 执行文件解析（parse_dwg/parse_prt）
- 执行拆图操作（split_subgraphs）
- 将结果保存到Redis和PostgreSQL
- 更新任务进度（20%）

**FeatureRecognitionAgent（特征识别Agent）**：
- 调用feature-recognition-mcp服务
- 使用ThreadPoolExecutor并行处理多个子图（最多8个线程）
- 识别每个子图的特征（线割长度、厚度）
- 检测缺失参数，生成missing_params列表
- 更新子图状态和特征数据

**NCTimeAgent（NC时间Agent）**：
- 调用nc-connector-mcp服务
- 调用外部统一NC Agent（一次调用返回钻孔、开粗、精铣三种时间）
- 实现超时控制（60秒）
- 实现重试机制（3次，指数退避：1s、2s、4s）
- 降级处理（超时或失败时使用默认值）
- 生成警告信息

**InteractionAgent（交互Agent）**：
- 检查参数完整性
- 生成交互卡片（missing_input类型）
- 定义输入字段（类型、标签、默认值、验证规则）
- 暂停工作流，等待用户响应
- 处理用户提交或重新识别请求

**DecisionAgent（工艺决策Agent）**：
- 直接查询PostgreSQL数据库（不使用RAG）
- 检查用户覆盖参数
- 应用工艺规则（基于厚度、精度要求等）
- 输出工艺参数（wire_mode、wire_passes）
- 记录决策依据和应用的规则ID

**PricingAgent（计价Agent）**：
- 调用pricing-server-mcp服务
- 执行价格匹配（数据库查询+条件过滤）
- 计算基础成本（面积×单价或时间×时薪）
- 应用特殊规则（慢丝加成1.8倍、批量折扣0.95倍等）
- 汇总总成本（线割+NC+管理费）
- 生成OpResult结构

**ReportAgent（报表Agent）**：
- 调用report-generator-mcp服务
- 收集完整数据（任务信息、子图详情、价格引用、规则引用、用户交互）
- 生成Excel报表（4个Sheet）
- 生成PDF报表（可选）
- 保存到MinIO并生成下载链接
- 更新任务状态为completed


#### 2.2.6 实时通信系统
使用WebSocket实现前后端实时通信：
- **连接管理**: 每个任务建立独立WebSocket连接
- **心跳机制**: 每30秒发送ping/pong保持连接
- **消息格式**: JSON结构，包含job_id、status、stage、progress、message
- **事件类型**: 
  - initializing（初始化）
  - cad_parsing（CAD解析）
  - feature_recognition（特征识别）
  - waiting_input（等待用户输入）
  - decision（工艺决策）
  - pricing（价格计算）
  - report_generation（报表生成）
  - completed（完成）
  - failed（失败）
- **断线重连**: 前端自动重连，后端保留最近10条消息

## 四、详细业务流程实现

### 3.1 阶段0：文件上传与任务创建

**技术实现**：
1. 前端使用React + Ant Design构建文件上传组件，支持拖拽上传
2. 支持同时上传DWG和PRT两个文件，或单独上传其中一个
3. 使用FormData封装文件，通过axios发送POST请求到API网关
4. API网关接收请求后，生成唯一request_id（UUID v4）
5. 验证JWT Token，从Token中提取user_id
6. 检查文件格式（通过文件扩展名和MIME类型双重验证）：
   - DWG文件：application/acad, application/x-acad, image/vnd.dwg
   - PRT文件：application/x-prt, model/prt
7. 检查文件大小（每个文件限制100MB以内）
8. 调用ClamAV进行病毒扫描（通过clamd Python客户端）
9. 将文件流式上传到MinIO的files bucket：
   - DWG文件：生成dwg_file_id，保存到/dwg/{year}/{month}/{dwg_file_id}.dwg
   - PRT文件：生成prt_file_id，保存到/prt/{year}/{month}/{prt_file_id}.prt
10. 在PostgreSQL的jobs表中创建记录：
    - 保存dwg_file_id、dwg_file_name、dwg_file_path、dwg_file_size
    - 保存prt_file_id、prt_file_name、prt_file_path、prt_file_size
    - 初始状态为pending
11. 构造消息体，发送到RabbitMQ的job_processing队列
12. 返回HTTP 200响应，包含job_id和状态
13. 前端收到响应后，建立WebSocket连接或开始轮询任务状态

**文件上传策略**：
- **必须上传DWG文件**：用于2D拆图和线割识别
- **可选上传PRT文件**：用于NC加工时间计算
- 如果只上传DWG文件：
  - 可以完成线割成本计算
  - NC加工时间需要用户手动输入或使用默认值
- 如果同时上传DWG和PRT文件：
  - 可以完成完整的成本计算
  - NC加工时间通过调用外部NC Agent自动计算

**错误处理**：
- 文件格式不支持：返回400错误，提示支持的格式
- 文件过大：返回413错误，提示文件大小限制
- 病毒检测：返回403错误，拒绝上传
- MinIO上传失败：返回500错误，记录详细日志
- 未上传DWG文件：返回400错误，提示DWG文件必须上传

**性能优化**：
- 使用流式上传，避免内存占用过大
- MinIO使用分片上传，支持断点续传
- 异步处理，上传完成立即返回，不阻塞用户
- 两个文件可以并行上传到MinIO

### 4.1 阶段1：异步任务处理与编排引擎启动

**技术实现**：
1. RabbitMQ Consumer（orchestrator_worker）监听job_processing队列
2. 使用Celery或自定义Worker实现，配置4个Worker进程，每个并发2个任务
3. Worker接收到消息后，实例化OrchestratorAgent
4. OrchestratorAgent更新jobs表状态为processing
5. 创建执行上下文（context），包含job_id、user_id、file_path、version_lock
6. 将context保存到Redis（key: job:job_id:context，TTL: 24小时）
7. 使用LangGraph初始化状态机，定义8个节点和转换条件
8. 加载配置文件（从本地文件系统或配置中心读取YAML）
9. 记录操作日志到operation_logs表
10. 通过WebSocket推送初始状态（stage: initializing, progress: 0）

**LangGraph状态机设计**：
- **节点定义**: cad_parsing → feature_recognition → parameter_check → decision → pricing → report_generation → audit → completed
- **条件转换**: parameter_check节点根据参数完整性决定是否进入user_interaction节点
- **状态持久化**: 每个节点执行完成后，更新Redis中的context
- **异常处理**: 任何节点抛出异常，状态机转换到failed节点

**并发控制**：
- 使用Redis分布式锁（SETNX命令）防止同一任务重复执行
- 锁的key为job:job_id:lock，TTL为10分钟
- 获取锁失败时，返回任务已在处理中的错误


### 4.2 阶段2：CAD解析与拆图

**技术实现**：
1. OrchestratorAgent调用CADAgent的process方法
2. CADAgent通过MCP协议连接cad-parser-mcp服务（HTTP或gRPC）
3. 根据上传的文件类型调用相应的解析工具：
   - 如果有DWG文件：调用parse_dwg工具，传入dwg_file_path
   - 如果有PRT文件：调用parse_prt工具，传入prt_file_path
4. CAD解析服务使用Open CASCADE Technology（OCCT）或类似CAD内核
5. 解析DWG文件：
   - 读取图层信息
   - 读取几何实体（线、圆、多段线）
   - 读取尺寸标注
   - 读取文本注释
6. 解析PRT文件：
   - 读取3D实体
   - 读取曲面
   - 读取特征树
7. 调用split_subgraphs工具，执行拆图算法（主要针对DWG文件）：
   - **按图层拆分**: 识别图层命名规则（如WIRE_CUT_1、WIRE_CUT_2），将同一图层的实体分组
   - **按封闭轮廓拆分**: 遍历所有多段线，检查起点终点是否重合，计算轮廓边界框
   - **按空间位置拆分**: 使用DBSCAN聚类算法（sklearn库），将空间上接近的实体分组
8. 为每个子图生成唯一ID（格式：UP01、UP02...）
9. 计算每个子图的边界框（min_x, min_y, max_x, max_y）
10. 将拆图结果保存到Redis的context中，同时保存DWG和PRT文件路径
11. 在PostgreSQL的subgraphs表中为每个子图创建记录，初始状态为pending
12. 更新jobs表的total_subgraphs字段和progress字段（20%）
13. 通过WebSocket推送进度（stage: cad_parsing, progress: 20, subgraphs: [...]）

**文件关联**：
- DWG文件用于拆图和线割识别
- PRT文件用于NC加工计算
- 在context中同时保存两个文件的路径，供后续Agent使用

**拆图算法详解**：
- **图层识别**: 使用正则表达式匹配图层名称，提取工艺类型（WIRE、DRILL、MILL等）
- **封闭轮廓检测**: 计算多段线的起点和终点距离，小于0.01mm视为封闭
- **DBSCAN聚类**: 设置eps=10mm（实体间最大距离），min_samples=3（最小实体数）
- **边界框计算**: 遍历所有实体的顶点，找到最小和最大的x、y坐标

**性能优化**：
- CAD解析服务使用C++实现核心算法，通过Python绑定调用
- 大文件分块读取，避免内存溢出
- 拆图算法使用多线程并行处理不同图层

### 4.3 阶段3：并行处理 - 特征识别与NC时间计算

**技术实现**：
1. OrchestratorAgent使用asyncio.gather同时启动两个分支
2. **分支A - 特征识别**：
   - 调用FeatureRecognitionAgent的process方法
   - 连接feature-recognition-mcp服务
   - 使用ThreadPoolExecutor创建线程池（max_workers=8）
   - 对每个子图提交识别任务到线程池
   - 每个任务执行：
     - 识别封闭轮廓（检查多段线封闭性）
     - 计算线割长度（周长 = 所有线段长度之和）
     - 提取厚度信息（从尺寸标注的文本中解析数字，或从文本注释中提取）
     - 判断是否需要线割（封闭轮廓且厚度>0）
     - 计算置信度（基于轮廓封闭性、厚度提取成功率）
   - 等待所有任务完成，收集结果
   - 检测缺失参数（thickness_mm为null的子图）
   - 更新subgraphs表的特征数据

3. **分支B - NC时间计算**：
   - 调用NCTimeAgent的process方法
   - 连接nc-connector-mcp服务
   - 检查是否上传了PRT文件：
     - 如果有PRT文件：调用外部统一NC Agent
     - 如果没有PRT文件：跳过NC计算或使用默认值
   - 调用外部统一NC Agent：
     - **统一NC Agent**: POST请求到http://nc-agent:8001/api/nc/estimate_complete
     - 输入：完整PRT文件路径、材料类型
     - 输出：钻孔时间、开粗时间、精铣时间（一次返回全部）
   - 设置超时（60秒）
   - 实现重试机制：使用tenacity库，最多重试3次，指数退避（1s、2s、4s）
   - 降级处理：超时或失败时，从历史数据表查询平均值，或使用配置的默认值
   - 生成警告信息（如"NC Agent超时，使用默认值"或"未上传PRT文件，NC时间使用默认值"）
   - 汇总NC时间和成本

4. 等待两个分支都完成（asyncio.gather返回）
5. 将结果聚合到context中
6. 更新Redis和PostgreSQL
7. 通过WebSocket推送进度（stage: feature_recognition, progress: 50）

**并发控制**：
- 特征识别使用线程池，避免GIL影响（因为调用的是C++库）
- NC时间计算使用协程，充分利用IO等待时间
- 两个分支完全独立，互不阻塞

**错误处理**：
- 特征识别失败：记录错误日志，该子图标记为识别失败，继续处理其他子图
- NC Agent超时：使用默认值，生成review卡片提示人工复核
- NC Agent失败：使用历史平均值或默认值

### 4.5 阶段5：工艺决策

**技术实现**：
1. OrchestratorAgent调用DecisionAgent的process方法
2. DecisionAgent遍历每个子图，执行工艺决策
3. 对于每个子图：
   - 检查用户覆盖参数（从context.user_overrides中读取）
   - 如果用户指定了工艺参数（如"UP01本次按照快丝割一刀"），直接使用
   - 否则，查询PostgreSQL的process_rules表：
     ```sql
     SELECT * FROM process_rules
     WHERE feature_type = 'WIRE'
       AND thickness_mm >= 10
       AND thickness_mm < 50
       AND version_id = 'v1.0'
       AND is_deleted = false
     ORDER BY priority DESC
     LIMIT 1
     ```
   - 应用决策逻辑：
     - 默认规则：厚度10-50mm，使用中丝+割一刀
     - 厚度>50mm：使用慢丝
     - 精度要求高（从图纸标注中提取公差）：使用慢丝+割一修一
   - 输出工艺参数：wire_mode（fast/mid/slow）、wire_passes（cut1/cut1_trim1等）
   - 记录应用的规则ID和决策原因
4. 更新subgraphs表的工艺参数
5. 写入operation_logs表
6. 通过WebSocket推送进度（stage: decision, progress: 70）

- 支持复杂条件表达式（如thickness_mm >= 10 AND thickness_mm < 50）
- 支持优先级排序（priority字段，数值越大优先级越高）
- 支持版本管理（version_id字段，支持多版本并存）
- 支持规则启用/禁用（is_deleted字段）

**用户覆盖机制**：

### 4.6 阶段6：价格匹配与成本计算

**技术实现**：
1. OrchestratorAgent调用PricingAgent的process方法
2. PricingAgent连接pricing-server-mcp服务
3. 对每个子图执行价格匹配：
   - 查询PostgreSQL的price_items表：
     ```sql
     SELECT id, unit_price, unit, param_conditions, priority
     FROM price_items
     WHERE version_id = 'v1.0'
       AND feature_type = 'WIRE'
       AND is_deleted = false
     ```
   - 过滤匹配：检查param_conditions（JSON字段），验证thickness_mm、wire_mode等参数是否在范围内
   - 匹配结果处理：
     - 匹配到1条：直接使用该价格
     - 匹配到多条：按priority排序，选择优先级最高的，或生成选择卡片让用户选择
     - 无匹配：使用兜底价格（从配置文件读取默认单价）
4. 计算基础成本：
   - 线割成本 = wire_length_mm × thickness_mm × unit_price
   - 示例：1234.56mm × 10mm × 0.05元/mm² = 617.28元
5. 应用特殊规则：
   - 慢丝割一修一：成本 × 1.8
   - 批量折扣（子图数量>10）：成本 × 0.95
   - 材料加成（不锈钢）：成本 × 1.2
   - 规则从special_rules表查询，支持动态配置
6. 计算NC加工成本：
   - 钻孔成本 = drilling_time_minutes / 60 × hourly_rate
   - 开粗成本 = roughing_time_minutes / 60 × hourly_rate
   - 精铣成本 = milling_time_minutes / 60 × hourly_rate
   - 时薪从配置表读取（如600元/小时）
7. 汇总总成本：
   - 线割成本小计
   - NC加工成本小计
   - 管理费（总成本的10%）
   - 总计
8. 生成OpResult结构：
   - status: ok/warning/error
   - total_cost: 总成本
   - breakdown: 成本明细
   - refs: 引用的价格和规则ID
   - review_items: 需要人工复核的项目
9. 更新subgraphs表和jobs表
10. 通过WebSocket推送进度（stage: pricing, progress: 85）

**价格匹配算法详解**：
- param_conditions字段存储JSON格式的条件：
  ```json
  {
    "thickness_mm": {"min": 10, "max": 50},
    "wire_mode": ["mid", "slow"]
  }
  ```
- 匹配时，逐个检查条件是否满足
- 支持范围条件（min/max）、枚举条件（数组）、正则表达式条件

**特殊规则引擎**：
- 规则以插件形式实现，支持动态加载
- 每个规则实现apply方法，接收成本和参数，返回调整后的成本
- 规则按优先级顺序应用，支持规则链
- 记录每个规则的应用情况，便于审计

### 4.9 重算功能实现

**单个子图重算**：
1. 用户在前端点击子图的"重算"按钮
2. 前端发送POST请求到/api/v1/jobs/{job_id}/subgraphs/{subgraph_id}/recalculate

4. API网关验证权限（检查用户是否有重算权限）

6. 创建重算记录到recalculations表
7. 记录审计日志到audit_logs表
8. 发送消息到RabbitMQ的recalculation_queue
9. RecalculationAgent接收消息：
   - 加载原始数据（从subgraphs表）
   - 应用修改参数（如thickness_mm从10改为12）
   - 保存修改前的快照到price_histories表
   - 重新执行工艺决策（调用DecisionAgent）
   - 重新执行价格计算（调用PricingAgent）
   - 计算成本差异（新成本 - 原成本）
   - 更新subgraphs表和jobs表
   - 更新recalculations表状态为completed
10. 重新生成报表（调用ReportAgent）
11. 通过WebSocket推送重算完成（event: recalculation_completed, changes: {...}）

**批量子图重算**：
1. 用户勾选多个子图，点击"批量重算"按钮
2. 前端发送POST请求到/api/v1/jobs/{job_id}/recalculate/batch
3. 请求体包含：subgraph_ids数组、reason、apply_new_version（新版本信息）
4. API网关验证权限和子图数量（最多50个）
5. 创建批量重算任务到batch_recalculations表
6. 为每个子图创建重算记录到recalculations表
7. 为每个子图发送独立消息到RabbitMQ
8. 多个Worker并行处理（最多4个Worker）
9. 定时检查批量重算进度（每5秒查询一次数据库）
10. 通过WebSocket推送进度（progress: 66%, completed: 2/3）
11. 所有子图重算完成后：
    - 汇总统计（成功数、失败数、总成本变化）
    - 更新batch_recalculations表状态
    - 重新生成完整报表
    - 通过WebSocket推送批量重算完成

**重算性能优化**：
- 使用消息队列实现异步处理，避免阻塞
- 批量重算使用并行处理，提高效率
- 重算只更新变化的数据，不重新执行所有步骤
- 使用数据库事务，确保数据一致性

## 六、技术难点与解决方案

### 6.1 CAD文件解析与拆图

**难点**：
- DWG和PRT文件格式复杂，需要专业的CAD内核
- 拆图算法需要识别多种情况（图层、封闭轮廓、空间位置）
- 大文件解析性能问题

**解决方案**：
- 使用Open CASCADE Technology（OCCT）开源CAD内核，支持多种CAD格式
- 实现三种拆图策略，优先使用图层识别，其次使用封闭轮廓检测，最后使用DBSCAN聚类
- 使用C++实现核心算法，通过pybind11提供Python接口
- 大文件分块读取，使用流式处理
- 添加缓存机制，避免重复解析

### 6.2 并发控制与性能优化

**难点**：
- 多个子图需要并行处理，但要控制并发数量
- 外部NC Agent调用可能超时或失败
- 数据库并发写入可能导致死锁

**解决方案**：
- 使用ThreadPoolExecutor控制线程池大小（max_workers=8）
- 使用asyncio.gather实现异步并发调用
- 实现超时重试机制（tenacity库，最多3次，指数退避）
- 实现降级策略（使用默认值或历史平均值）
- 使用Redis分布式锁防止重复执行
- 使用数据库连接池（SQLAlchemy，pool_size=20）
- 使用乐观锁（version字段）防止并发更新冲突

### 6.3 用户交互与工作流暂停

**难点**：
- 工作流需要在参数缺失时暂停，等待用户输入
- 用户可能长时间不响应，需要处理超时
- 工作流恢复时需要保持状态一致性

**解决方案**：
- 使用LangGraph的条件节点实现工作流分支
- 将执行上下文保存到Redis，TTL设置为24小时
- 用户提交后，从Redis恢复上下文，发送消息到RabbitMQ恢复工作流
- 超时处理：24小时后自动标记任务为超时，发送通知给用户
- 使用数据库事务确保状态一致性

### 6.4 价格匹配与规则引擎

**难点**：
- 价格匹配条件复杂，需要支持多种条件类型
- 特殊规则需要动态配置，不能硬编码
- 价格和规则需要支持版本管理

**解决方案**：
- 使用JSON字段存储条件（param_conditions），支持范围、枚举、正则表达式
- 实现规则引擎，支持规则链和优先级
- 规则以插件形式实现，支持动态加载
- 使用version_id字段实现版本管理，支持多版本并存
- 价格变更时，创建新版本，旧版本标记为历史版本
- 任务执行时锁定版本（version_lock），确保重算时使用相同版本

### 6.5 报表生成与文件管理

**难点**：
- Excel报表需要复杂的样式和格式
- PDF报表需要支持中文和特殊字符
- 文件下载需要支持大文件和断点续传

**解决方案**：
- 使用openpyxl库生成Excel，支持丰富的样式
- 使用ReportLab库生成PDF，配置中文字体（如SimHei）
- 使用MinIO的预签名URL实现安全下载
- 设置URL有效期（24小时），防止链接泄露
- MinIO支持断点续传和分片下载
- 报表生成使用异步任务，避免阻塞

### 6.6 审计与合规性

**难点**：
- 需要记录所有操作，便于审计
- 数据需要长期保留（7年）
- 需要防止数据篡改

**解决方案**：
- 使用audit_logs表记录所有数据变更，包含before和after快照
- 使用operation_logs表记录所有Agent操作
- 使用price_histories表记录价格历史快照
- 归档数据使用tar.gz压缩，计算MD5校验和
- MinIO设置对象不可变（immutable），防止篡改
- 使用MinIO的版本控制功能，支持数据恢复
- 定期备份数据库和MinIO数据

## 八、安全设计

### 8.1 认证与鉴权

**认证机制**：
- 使用JWT Token进行用户认证
- Token包含：user_id、username、roles、exp（过期时间）
- Token有效期：2小时（access_token）+ 7天（refresh_token）
- 使用RS256算法签名，私钥存储在密钥管理服务中

**鉴权机制**：
- 基于角色的访问控制（RBAC）
- 角色定义：管理员、操作员、查看者
- 权限定义：上传文件、查看任务、重算、修改价格、修改规则
- 每个API接口检查用户权限

### 8.2 数据安全

**传输安全**：
- 所有API使用HTTPS（TLS 1.3）
- WebSocket使用WSS（WebSocket Secure）
- 内部服务间通信使用mTLS（双向TLS）

**存储安全**：
- 数据库连接使用SSL
- MinIO启用服务端加密（SSE-S3）
- 敏感数据（如密码）使用bcrypt加密
- 审计日志不可修改（append-only）

**文件安全**：
- 文件上传前进行病毒扫描（ClamAV）
- 限制文件类型（只允许DWG、PRT）
- 限制文件大小（最大100MB）
- 文件存储使用随机文件名，防止路径遍历攻击

### 8.3 防护措施

**DDoS防护**：
- 使用Nginx限流（limit_req_zone）
- API网关限流（每用户每分钟100次请求）
- 使用CDN加速和防护（如Cloudflare）

**SQL注入防护**：
- 使用ORM（SQLAlchemy）参数化查询
- 禁止拼接SQL语句
- 数据库用户权限最小化

**XSS防护**：
- 前端使用React自动转义
- 后端返回数据进行HTML转义
- 设置Content-Security-Policy头

**CSRF防护**：
- 使用CSRF Token
- 检查Referer头
- SameSite Cookie属性

## 十一、第二期特殊场景（扩展功能）

以下功能作为第二期需求，在第一期核心功能稳定后开发：

### 11.1 线割改精铣场景（2D转3D）

**业务场景**：
用户在查看成本结果后，发现某个子图使用线割成本较高，希望改用精铣工艺。系统需要将2D线割轮廓拉伸为3D实体，传入NC精铣Agent计算成本。

**技术实现**：
1. 前端提供"工艺调整"功能，用户选择"改用精铣"
2. 用户输入拉伸高度（如10mm）
3. 后端调用CADAgent的extrude_2d_to_3d方法
4. 调用cad-parser-mcp的extrude_2d工具：
   - 读取2D封闭轮廓（线割红色线条）
   - 验证轮廓封闭性
   - 沿Z轴拉伸指定高度
   - 生成3D实体（PRT格式）
   - 标记需要精铣的面（原2D红色线对应的侧面）
5. 调用NCTimeAgent的call_milling方法
6. 发送HTTP请求到外部统一NC Agent：
   - 传入3D PRT文件
   - 传入标记的面ID列表
   - 指定精铣参数（公差、材料等）
   - 工艺类型指定为milling
7. 外部NC Agent返回精铣时间和成本
8. 重新计算总成本，对比原线割成本
9. 更新数据库，记录工艺变更
10. 生成新报表，标注工艺变更信息

**关键技术**：
- 2D转3D拉伸算法（使用OCCT的BRepPrimAPI_MakePrism）
- 3D面标记算法（根据2D轮廓投影到3D侧面）
- 工艺变更记录（process_changes表）

### 11.2 单个子图3D传入NC场景

**业务场景**：
用户需要单独计算某个子图的NC加工成本，需要从完整3D PRT文件中拆分出该子图对应的3D部分，传入NC Agent。

**技术实现**：
1. 前端提供"单独NC计算"功能
2. 后端调用CADAgent的split_3d_prt方法
3. 调用cad-parser-mcp的split_3d_by_region工具：
   - 加载完整3D PRT文件
   - 根据2D子图的边界框（bbox）定位3D区域
   - 投影2D边界框到3D空间
   - 识别该区域内的3D实体
   - 切割3D实体，提取子图部分
   - 生成独立的3D PRT文件（如UP02_single.prt）
4. 调用NCTimeAgent的call_nc_for_single方法
5. 调用外部统一NC Agent：
   - **统一NC Agent**: POST请求到http://nc-agent:8001/api/nc/estimate_single
   - 输入：单个子图PRT文件、材料类型
   - 输出：钻孔时间、开粗时间、精铣时间
6. 汇总NC时间和成本
7. 更新数据库，记录单独NC计算结果
8. 前端显示该子图的NC成本明细

**关键技术**：
- 3D PRT拆分算法（使用OCCT的BRepAlgoAPI_Cut）
- 2D边界框到3D空间的投影
- 3D实体的空间查询和过滤

### 11.3 板料线生成场景

**业务场景**：
系统在接收到DWG和PRT文件后，自动为每个2D子图生成板料线（外框线），用于后续的板料切割工艺。

**技术实现**：
1. 在工作流中插入板料线生成步骤（在CAD解析后，特征识别前）
2. OrchestratorAgent调用SheetLineAgent的process方法
3. SheetLineAgent使用ThreadPoolExecutor并行处理所有子图
4. 对每个子图：
   - 获取封闭轮廓的所有点
   - 计算轮廓边界框
   - 使用偏移算法生成外框（向外偏移5mm）
   - 处理圆角和尖角（使用Clipper库）
   - 确保外框封闭性
   - 添加工艺标记（图层名称、线型、颜色）
   - 保存板料线数据（坐标点、面积、周长）
5. 生成带板料线的DWG文件（可选）：
   - 创建新图层"SHEET_LINE"
   - 在新图层上绘制板料线（绿色虚线）
   - 保存为新DWG文件（complete_with_sheet.dwg）
6. 更新数据库，记录板料线信息
7. 继续执行后续步骤（特征识别、NC时间计算等）

**关键技术**：
- 轮廓偏移算法（使用Clipper库的ClipperOffset）
- 圆角和尖角处理（设置JoinType为jtRound或jtMiter）
- DWG文件编辑（使用OCCT或ezdxf库）

### 11.4 多工艺并行处理场景

**业务场景**：
同一个任务需要多种工艺并行处理，如线割、NC加工、磨床加工、电火花加工等，系统需要支持动态加载多个工艺Agent，并行计算成本。

**技术实现**：
1. 在workflow_config.yaml中配置启用的工艺：
   ```yaml
   enabled_processes:
     - WIRE
     - NC
     - GRINDING
     - EDM
   ```
2. OrchestratorAgent读取配置，动态加载Agent：
   - 从agent_registry.yaml读取Agent类名和模块路径
   - 使用importlib动态导入Agent类
   - 实例化所需的Agent（WireAgent、NCAgent、GrindingAgent、EDMAgent）
3. 使用asyncio.gather并行启动多个工艺Agent
4. 每个Agent独立执行：
   - WireAgent：处理线割子图，计算线割成本
   - NCAgent：调用外部NC Agent，计算NC成本
   - GrindingAgent：调用外部磨床Agent，计算磨削成本
   - EDMAgent：调用外部电火花Agent，计算电火花成本
5. 等待所有Agent完成，收集结果
6. 汇总所有工艺成本：
   - 线割成本小计
   - NC加工成本小计
   - 磨床加工成本小计
   - 电火花加工成本小计
   - 管理费
   - 总计
7. 更新数据库，记录多工艺结果
8. 生成多工艺报表：
   - 添加"多工艺成本汇总"Sheet
   - 显示各工艺成本和占比
   - 生成成本饼图
9. 前端显示多工艺成本对比

**关键技术**：
- 动态Agent加载（使用importlib和反射）
- 多工艺并行执行（使用asyncio.gather）
- 扩展Agent注册机制（agent_registry.yaml）
- 多工艺报表生成（openpyxl图表功能）

**扩展Agent示例**：
- **GrindingAgent**：调用外部磨床Agent（http://grinding:8004/api/grinding/estimate），计算磨削时间和成本
- **EDMAgent**：调用外部电火花Agent（http://edm:8005/api/edm/estimate），计算电火花加工时间和成本
- **LaserAgent**：调用外部激光切割Agent，计算激光切割成本
- **WeldingAgent**：调用外部焊接Agent，计算焊接成本
